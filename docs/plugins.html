Plugin development

Customize PI WEB with trusted plugins.

What can be extended

Plugins can add focused UI and workspace integrations to PI WEB:

  • Action palette commands for custom workflows.
  • Workspace tools and panels next to Files and Terminal.
  • Workspace labels in the workspace list, header, and status bar.
  • Browser-public assets served only from an explicit browserRoot.
  • Browser helpers for files, terminals, prompts, rendering, and paired backends.
  • One workspace provider from an optional sessiond server entry.

The server API is deliberately narrow: lifecycle callbacks, scoped logging/settings, bounded argv execution, one workspace provider, JSON backend requests, and removal planning. Plugins receive no raw Fastify access, arbitrary routes, concrete services, generic event bus, Pi model-provider registration, or general server hooks.

The plugin API is intentionally limited and actively developed. Feedback is appreciated: if an extension point is missing, unclear, or awkward, please open a GitHub issue.

Pi packages, Pi extensions, and PI WEB plugins

Pi packages are distribution bundles managed by Pi (pi install, pi remove, pi update). A Pi package can provide Pi extensions, skills, prompt templates, themes, context/system prompt files, and/or PI WEB plugins. Many Pi packages do not include a PI WEB plugin.

Pi extensions are runtime modules loaded by the session daemon. They can register Pi tools, hooks, commands, and model providers. They are not PI WEB plugins.

PI WEB plugins are packages discovered from bundled, local, dev, and installed Pi-package sources. They can declare a browser module, a sessiond serverModule, or both. Their server API is separate from Pi extensions and cannot register Pi model providers or arbitrary hooks. Plugin enablement is PI WEB config; package installation is a separate Pi package-manager task.

Use Settings → Pi packages to view configured Pi packages or install/remove/update a package. Enter only the package source, such as npm:@scope/package, a git/URL source, or a local path. PI WEB uses Pi's default package location, equivalent to pi install <source>, and does not ask for an install location.

When machine federation is enabled, Settings → Pi packages targets the currently selected machine. The panel labels whether changes will run on the local/gateway machine or on a selected remote PI WEB machine.

Use Settings → PI WEB plugins to edit desired plugin enablement on the selected machine and compare it with sessiond's active startup snapshot. Browser-only changes apply after a page reload. Server-backed changes require a session-daemon restart and then a page reload. Unsupported or unavailable remote settings are reported instead of silently falling back to the gateway.

After installing, removing, or updating a Pi package, type /reload in each idle PI WEB session on the target machine to refresh ordinary Pi resources such as extensions, skills, prompt templates, themes, and context/system prompt files. Reload the browser page separately for newly discovered or changed PI WEB browser plugins. If a PI WEB package has a server entry, manually restart sessiond first. A provider-registering Pi extension follows a separate daemon-start policy; see Pi extension provider baseline.

Pi extension dialogs in PI WEB

Pi extensions running under PI WEB's session daemon can ask the user questions with ctx.ui.confirm(), ctx.ui.select(), and ctx.ui.input(). For these three methods ctx.hasUI is true in fact: the call renders a dialog card inline in the session transcript — including from session_start hooks while the session is still starting and from in-flight tool_call hooks — and resolves with the user's actual answer.

Answers travel over a dedicated session-daemon channel, never the prompt queue, so a parked tool_call hook cannot deadlock the run. Open dialogs survive browser reloads, the first answer wins across tabs, and unanswered dialogs settle safely: aborting the run or replacing the runtime resolves them immediately with the kind's cancel value (false for confirm, undefined for select and input), and the effective deadline — the sooner of the extension's own timeout and the daemon's extensionDialogsTimeoutMs safety valve (default 5 minutes, 0 waits forever) — does the same when no one answers. Other ExtensionUIContext surfaces (widgets, status, editor, custom) remain no-ops despite hasUI === true.

For the full behavior notes and author guidance, read plugins.md; for the timeout key, see Extension dialogs in the configuration reference.

What to ask AI to build

You do not need to hand-code plugins. Give an AI agent a clear goal, the workspace/project facts it should use, and the PI WEB plugin rules.

  • Show a workspace badge from a repo file, environment file, branch name, container, or dev URL.
  • Add a workspace panel that summarizes project-specific health, commands, links, or runbooks.
  • Add action-palette commands for common project workflows or prompts.
  • Add links to local services, preview deployments, dashboards, CI, logs, or docs.

Canonical examples

The repository and published npm package include a standalone dual-entry workspace-provider example. Copy examples/workspace-provider-plugin/ for package metadata, a strict NodeNext TypeScript build, browser/server source, and concise install guidance. It conservatively claims only projects with an opt-in marker, publishes non-secret metadata, and calls the backend that owns the workspace without Git-specific behavior or PI WEB internal imports.

Bundled Info remains the small browser-only example under pi-web-plugins/info/. Bundled Git is the production provider example; its browser entry moved to pi-web-plugins/git/browser/pi-web-plugin.ts, while its server entry is pi-web-plugins/git/server-plugin.ts.

Dual-entry package metadata 
{
  "type": "module",
  "piWeb": {
    "plugins": [{
      "id": "workspaces",
      "browserRoot": "dist/browser",
      "module": "dist/browser/index.js",
      "serverModule": "dist/server.js",
      "machineSpecific": true
    }]
  }
}
Public TypeScript imports 
import type { PiWebPlugin } from "@jmfederico/pi-web/plugin-api";
import type { PiWebServerPlugin, WorkspaceProvider } from "@jmfederico/pi-web/server-plugin-api";

Browser v2, server v1, and the package boundary

Browser entries default-export { apiVersion: 2, name, activate }. The host rejects v1 with an attributed unsupported-version error; no browser-v1 shim is provided. Server entries remain on apiVersion: 1. During migration, replace browser-v1 Git aliases, including top-level workspace.branch, with provider metadata and refreshWorkspacePanels()/onInvalidate(). Generic presentation uses the provider-authored workspace.label; provider-specific facts belong in workspace.provider.metadata or the owning backend.

Browser activation pluginId is the stable package/source id on every machine and matches workspace.provider.pluginId. Use the separate host-unique runtimePluginId only for qualified contribution references. The only supported type entrypoints are the type-only exports @jmfederico/pi-web/plugin-api and @jmfederico/pi-web/server-plugin-api. The former plugin-api/unstable path and private dist/** deep imports are not contracts.

Browser and server module paths must use canonical package-relative form; empty or . segments, traversal, backslashes, and absolute or Windows drive-qualified paths are rejected. Each browser entry must declare a safe package-relative browserRoot containing its module; server-only entries must not declare one. Invalid, missing, package-escaping, symlink-escaping, or module-excluding roots fail discovery. Externally declared ids core, themes, and the machine.* namespace are reserved and rejected.

  • Only files logically and canonically inside browserRoot are served; everything else in the package stays outside plugin asset routes.
  • browserRoot: "." makes almost the whole scanned package browser-public, so prefer a narrow build directory and put no secrets inside it.
  • The package-wide scan allows at most 4,096 entries and 16 MiB of file content, excluding traversal into .git and node_modules; files outside the browser root still count.
  • Both .js and .mjs are served with executable JavaScript MIME types. Prefer module-relative asset URLs for federation and nested deployments.

Workspace provider contract

Sessiond is the single workspace authority. An enabled server entry can contribute at most one provider. Primary providers probe first; bundled Git probes only as a fallback. Exactly one claimant owns the whole project's workspace semantics. Multiple claimants in the winning tier produce a visible conflict rather than import-order selection. If nobody claims, the kernel project-folder workspace remains available.

A server module default-exports { apiVersion: 1, name, activate }. Activation may return cooperative start, stop, and health callbacks plus at most one provider. Every activation, lifecycle, provider, and request signal is scoped to that one invocation and is aborted when it times out or settles; it is not a plugin-lifetime shutdown signal. Release resources in explicit stop(). Server code is never hot-reloaded.

A provider returns stable workspace keys, accessible absolute directories, labels, exactly one main workspace, optional private JSON data, browser-visible publicMetadata, and optional request/removal capabilities. Public metadata is visible to all browser code and API consumers, so it must never contain secrets. capabilities.remove is true only for a workspace that advertises removal and whose owner implements it.

A removal plan approves a visible host-owned terminal run; it does not mean removal has completed. Its command is shell source interpreted by the host's login shell from a host-selected safe non-target working directory. Providers must use and shell-quote the supplied absolute workspace path, keep the operation in the foreground, and treat shell exit 0 as successful completion.

Panels and labels receive optional context.backend only when their browser entry has a paired active server backend. PI WEB binds backend.request(operation, input) to the original plugin id, active backend revision, selected machine, project, and workspace, and carries it through federation. Plugins should never construct PI WEB backend or machine API URLs. Panels can implement onInvalidate and actions can call refreshWorkspacePanels(); route aliases and shortcut aliases exist only for browser-v1 migrations.

PI WEB ships only bundled Git as a production provider. Third parties own replacement integrations such as Jujutsu providers. An installed primary provider can claim its projects and suppress fallback Git without PI WEB core changes; no reference replacement is shipped or promised here.

Built-in plugins

PI WEB ships core, discoverable plugins in the main @jmfederico/pi-web npm package. No separate pi install step is required. After updating PI WEB, restart sessiond so bundled server entries use the installed revision, then reload the browser. Browser-only bundled entries need only the page reload.

Built-in plugins can be managed from Settings → PI WEB plugins or with the top-level plugins config key.

Git

Git is enabled by default and is PI WEB's bundled fallback workspace provider. It discovers worktrees, owns Git removal plans and status/diff requests, and adds the paired Git panel. An enabled primary third-party provider can claim a project before Git. Disabling git and restarting sessiond leaves the kernel folder workspace plus generic Files, Terminal, and Session features; reload the browser so Git contributions disappear.

Updates

Updates adds a conditional Updates workspace tab with PI WEB update, restart, and installed-service guidance, plus a Check for PI WEB Updates action. It is built into PI WEB, enabled by default, and uses the selected machine's plugin copy when machine federation is active.

  • Plugin id: updates
  • Selected-machine status refreshes every 15 minutes while a browser tab is connected.
  • Automatic npm release lookups are cached for six hours; the action bypasses the caches and checks immediately.
Disable Updates 
{
  "plugins": {
    "updates": { "enabled": false }
  }
}

Workspace Tasks

Workspace Tasks adds a Tasks workspace tab for running configured shell commands in dedicated PI WEB terminals. It is built into PI WEB and enabled by default.

  • Plugin id: workspace-tasks
  • Config file: .pi-web/tasks.json
Disable Workspace Tasks 
{
  "plugins": {
    "workspace-tasks": { "enabled": false }
  }
}
Example .pi-web/tasks.json 
{
  "version": 1,
  "tasks": [
    {
      "id": "app.start",
      "title": "Start app",
      "group": "Development",
      "description": "Start the local development server.",
      "command": "npm run dev"
    },
    {
      "id": "db.reset",
      "title": "Reset DB",
      "group": "Database",
      "command": "go -C klingit-go run ./cli db reset",
      "confirm": true
    }
  ]
}

Open a workspace, choose the Tasks tab, and click Run next to a task. Commands run in the workspace root because PI WEB creates the terminal for that workspace.

Review task configs before running them, especially in shared projects. Workspace Tasks runs trusted shell commands from your repositories.

Manage PI WEB plugins

Settings → PI WEB plugins compares desired package/config state with the active sessiond startup snapshot on the selected machine. It reports browser-only, active, failed, incompatible, disabled, not-active, unknown, conflict, stale-revision, health, safe-mode, and restart-required states. Settings values remain private; diagnostics expose only revisions and fingerprints.

Package installation stays under Settings → Pi packages. Plugin enablement writes the selected machine's top-level plugins config key and remains editable while sessiond is unavailable, although active state cannot then be verified.

Plugin config shape 
{
  "plugins": {
    "git": { "enabled": true, "settings": {} },
    "info": { "enabled": false }
  }
}

Plugins default to enabled. A browser-only change applies after a page reload. A server entry captures enablement and JSON settings only at sessiond startup; replacing package files or saving config changes desired state without hot-reloading the active provider registry.

Lifecycle, restart, and offline recovery

  1. Install or update the plugin package on the target machine.
  2. Set its desired enablement/settings.
  3. For a browser-only plugin, reload the browser tab.
  4. For a server-backed plugin, restart sessiond, wait for it, then reload the browser tab.
Manual session-daemon restart: for the native systemd user service, run systemctl --user restart pi-web-sessiond (unit pi-web-sessiond.service). Restarting sessiond may interrupt active sessions and runtime ownership. Web/UI autoreload, restarting only web/API, browser reload, and Pi's /reload do not activate server-plugin changes.

Offline recovery edits config without contacting sessiond, discovering packages, or importing plugin code. Run these commands on the affected target machine; add --config /path/to/config.json when its services use a custom config.

Server-plugin recovery 
$ pi-web plugins disable <plugin-id> --restart
$ pi-web plugins safe-start show
$ pi-web plugins safe-start set bundled-only --restart
$ pi-web plugins safe-start set none --restart
$ pi-web plugins safe-start clear --restart
  • disable persists plugins.<id>.enabled: false while preserving unrelated config.
  • bundled-only filters discovery before external server packages are considered.
  • none imports no server plugins; the kernel folder workspace remains available.
  • clear restores ordinary configured discovery on the next start.
  • An unsupported serverPlugins.safeStart shape or value fails closed as effective none; use show, then set or clear, to repair it offline.
  • --restart acts automatically only for a recognized safe installation; otherwise PI WEB prints manual guidance. Config is durable before the restart attempt, so restart manually if that attempt fails.

Ordinary plugin failures are attributed and quarantined when the host can catch them. Safe start remains necessary because trusted in-process code can block or terminate sessiond. Every restart can interrupt active sessions/runtime ownership.

Remote machine plugins

With machine federation, the gateway loads compatible browser entries from the selected remote machine while server entries stay in that target's sessiond. Actions, panels, labels, file/terminal helpers, and context.backend.request() all follow the selected machine. Activation pluginId and workspace-provider ownership keep the stable source id; runtimePluginId may be machine-scoped so qualified contributions remain host-unique.

  • Paired backend requests carry the source plugin id and active target revision through the gateway.
  • Server-backed browser code is served only for an exact active package/source/scope/settings/revision pairing.
  • machineSpecific decides whether a browser-only gateway copy is portable; dual entries are always machine-specific.
  • Remote theme contributions remain ignored because themes are app-wide.
  • A current gateway reports missing/unsupported lifecycle or backend capabilities explicitly instead of falling back to gateway code.

Mixed-version provider/plugin operation is not supported in either upgrade order. A newer gateway rejects an older target's entire remote plugin manifest when it lacks the lifecycle contract, so that target's browser-only contributions and Git panel are unavailable. An older gateway still calls legacy core Git routes removed by an updated target, so remote Git status/diff returns 404. Upgrade the gateway and target together, restart their updated web/API processes and the target session daemon, then reload the gateway page. Other machine features use their own capability negotiation.

Select the remote machine in Settings → PI WEB plugins to edit desired state; the panel requires the target machine's plugin lifecycle support. Restart that remote session daemon for a server-backed change, then reload the gateway page.

Current manifests publish leading application-root module references. The browser keeps them inside the current application base, and the gateway rewrites accepted remote references for root and canonical trailing-slash nested deployments. Prefer module-relative assets such as new URL("./asset.json", import.meta.url); hard-coded /pi-web-plugins/<original-id>/... paths can point at the gateway copy.

Production usage

Local plugins work with the production native-service install. Put each package under ~/.pi-web/plugins/<plugin-id>/, or symlink it there while developing. No PI WEB rebuild is required. Browser-only entries need a page reload; server-backed entries need a sessiond restart followed by the page reload.

If PI_WEB_DATA_DIR is set, use $PI_WEB_DATA_DIR/plugins instead of ~/.pi-web/plugins.
Install a local plugin folder 
$ mkdir -p ~/.pi-web/plugins
$ ln -s /path/to/plugin-folder ~/.pi-web/plugins/plugin-id

AI-friendly docs

The full plugin reference is available as Markdown for AI agents to read, fetch, and follow: plugins.md.

If you want to understand the API yourself, ask an agent to read that file and explain the relevant public extension points for the plugin you want. Browser private routes/runtime fields, source internals, and dist/** declarations are not stable APIs. Use only the two documented type-only package exports for browser and server entries.

Develop and debug

  • Keep the source folder outside ~/.pi-web/plugins and symlink it in.
  • Build entry JavaScript at the exact package-relative paths declared in metadata, and keep the browser module/assets inside a narrow declared browserRoot.
  • Declare "type": "module" for a .js server entry or emit .mjs.
  • After browser-only edits, reload or hard-reload the tab and check its console.
  • After server edits, restart sessiond, reload the tab, and inspect pi-web logs.
  • Use Settings → PI WEB plugins for desired/active, health, conflict, and revision diagnostics.
Check discovered plugins 
$ curl http://127.0.0.1:8504/pi-web-plugins/manifest.json

For all contribution types and package metadata, read the Plugin API reference.

Trust model

Plugins are not sandboxed. Browser entries can use browser APIs, read/write workspace files through helpers, start terminal commands, and render arbitrary UI. Server entries execute in-process inside sessiond with the service user's filesystem, environment, and process permissions, and share sessiond's event loop. Install only packages you trust.

Ordinary import/lifecycle/health failures are quarantined when PI WEB can catch them, but server plugins are not crash-isolated. A CPU-bound, blocking, or deadlocked callback can stall sessions, terminals, and health endpoints. Abort signals and deadlines bound only cooperative asynchronous code and cannot preempt code that ignores them. This is a stability boundary, not a security boundary; offline disable and both safe-start levels are the recovery path.
