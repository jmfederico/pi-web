What can be extended

Plugins can add focused UI and workspace integrations to PI WEB:

  • Action palette commands for custom workflows.
  • Workspace tools and panels next to Files and Terminal.
  • Workspace labels in the workspace list, header, and status bar.
  • Browser-public assets served only from an explicit browserRoot.
  • Browser helpers for files, terminals, prompts, rendering, and exact-package peers.
  • Typed capabilities with exact-version dependency-aware startup and reverse disposal.
  • Host capabilities for package-scoped state, live workspace authority, and managed Pi conversations and initial runs.
  • One workspace provider from an optional sessiond server entry.
  • One package peer with independently optional JSON requests and bounded duplex channels.

The server API is deliberately narrow: lifecycle callbacks, typed capabilities, scoped logging/settings, bounded argv execution, one workspace provider, one package peer, host-governed services, and removal planning. Plugins receive no raw Fastify access, arbitrary routes, concrete services, generic service locator or event bus, Pi model-provider registration, or general server hooks.

The plugin API is intentionally limited and actively developed. Feedback is appreciated: if an extension point is missing, unclear, or awkward, please open a GitHub issue.

Pi packages, Pi extensions, and PI WEB plugins

Pi packages are distribution bundles managed by Pi (pi install, pi remove, pi update). A Pi package can provide Pi extensions, skills, prompt templates, themes, context/system prompt files, and/or PI WEB plugins. Many Pi packages do not include a PI WEB plugin.

Pi extensions are runtime modules loaded by the session daemon. They can register Pi tools, hooks, commands, and model providers. They are not PI WEB plugins.

PI WEB plugins are packages discovered from bundled, local, dev, and installed Pi-package sources. They can declare a browser module, a sessiond serverModule, or both. Their server API is separate from Pi extensions and cannot register Pi model providers or arbitrary hooks. Plugin enablement is PI WEB config; package installation is a separate Pi package-manager task.

Pi loads ordinary Pi resources from installed Pi packages and from its user and project resource locations. PI WEB plugin discovery loads only the declared browser and server entries; enabling or disabling a plugin does not add or remove the package's Pi extensions, skills, prompt templates, themes, or context/system prompt files.

Relay follows this split: installing or removing @jmfederico/pi-relay controls the human-gated /relay preparation prompt, its /relay-worktree compatibility alias, the tool-agnostic relay skill, and the opinionated relay-runner profile. Preparation builds a reviewable draft packet while establishing a shared understanding and only the first leg, then requires explicit approval before spawn_session; it does not pre-plan the chain. Fresh-worktree preparation moves the drafts into the target before dispatch. The runner keeps charter.md focused on the goal and scope edges, with execution mechanics in operations.md and project guidance as the quality authority. Relay completion requires both the chartered outcome and the review, approval, and delivery gates recorded in operations.md. The profile treats review as evidence gathering rather than a finding quota; re-review carries earlier decisions forward instead of restarting defect hunting. The normal path is an initial whole-work review plus one re-review when needed. A third attempt is an exceptional, justified contingency, after which a still-blocked Relay stops for human intervention. plugins.relays.enabled controls only the read-only Relays browser panel and its workspace action. Disabling the browser plugin leaves the Pi resources available. At session-daemon startup, PI WEB installs the package automatically for the active agent profile by default; removing it in Settings → Pi packages is remembered for that profile, and Available packages offers one-click reinstall.

Use Settings → Pi packages to view configured Pi packages or install/remove/update a package. Enter only the package source, such as npm:@scope/package, a git/URL source, or a local path. PI WEB uses Pi's default package location, equivalent to pi install <source>, and does not ask for an install location.

When machine federation is enabled, Settings → Pi packages targets the currently selected machine. The panel labels whether changes will run on the local/gateway machine or on a selected remote PI WEB machine.

Use Settings → PI WEB plugins to edit desired plugin enablement on the selected machine and compare it with sessiond's active startup snapshot. Browser-only changes apply after a page reload. Server-backed changes require a session-daemon restart and then a page reload. Unsupported or unavailable remote settings are reported instead of silently falling back to the gateway.

After installing, removing, or updating a Pi package, type /reload in each idle PI WEB session on the target machine to refresh ordinary Pi resources such as extensions, skills, prompt templates, themes, and context/system prompt files. Reload the browser page separately for newly discovered or changed PI WEB browser plugins. If a PI WEB package has a server entry, manually restart sessiond first. A provider-registering Pi extension follows a separate daemon-start policy; see Pi extension provider baseline.

Pi extension dialogs in PI WEB

Pi extensions running under PI WEB's session daemon can ask the user questions with ctx.ui.confirm(), ctx.ui.select(), and ctx.ui.input(). For these three methods ctx.hasUI is true in fact: the call renders a dialog card inline in the session transcript — including from session_start hooks while the session is still starting and from in-flight tool_call hooks — and resolves with the user's actual answer.

Answers travel over a dedicated session-daemon channel, never the prompt queue, so a parked tool_call hook cannot deadlock the run. Open dialogs survive browser reloads, the first answer wins across tabs, and unanswered dialogs settle safely: aborting the run or replacing the runtime resolves them immediately with the kind's cancel value (false for confirm, undefined for select and input), and the effective deadline — the sooner of the extension's own timeout and the daemon's extensionDialogsTimeoutMs safety valve (default 5 minutes, 0 waits forever) — does the same when no one answers. Other ExtensionUIContext surfaces (widgets, status, editor, custom) remain no-ops despite hasUI === true.

For the full behavior notes and author guidance, read plugins.md; for the timeout key, see Extension dialogs in the configuration reference.

What to ask AI to build

You do not need to hand-code plugins. Give an AI agent a clear goal, the workspace/project facts it should use, and the PI WEB plugin rules.

  • Show a workspace badge from a repo file, environment file, branch name, container, or dev URL.
  • Add a workspace panel that summarizes project-specific health, commands, links, or runbooks.
  • Add action-palette commands for common project workflows or prompts.
  • Add links to local services, preview deployments, dashboards, CI, logs, or docs.

Browser v4, server v3, and the package boundary

Browser entries default-export { apiVersion: 4, name, requires?, activate }; server entries use apiVersion: 3. Both hosts run bounded activate(), wait for every exact typed capability in requires, then call start({ capabilities, signal }). Contributions, peers, providers, and capability provisions publish only after start succeeds. The activation lifetimeSignal is aborted before rollback or shutdown cleanup, and bounded dispose(signal) runs in reverse dependency/start order.

Capability identity is the exact (pluginId, id, version) tuple. A provider can publish only identities owned by its stable plugin id; a consumer can resolve only tokens it declared in requires. Each token's parser validates and snapshots values across composition boundaries. Missing, invalid, duplicate, wrong-version, or cyclic dependencies fail the affected graph with attributed diagnostics while unrelated plugins continue. Browser and server capability graphs are separate; use the package peer to communicate across processes.

API v4/v3 deliberately replaces browser v2/server v1 without compatibility shims. Rename context.pairedBackend and ServerPluginActivation.pairedBackend to context.peer/ServerPluginActivation.peer; detect request and openChannel methods directly. Owner-backed context.backend, WorkspaceProvider.request(), and WorkspaceBackend are removed. Server start(signal) becomes start({ capabilities, signal }), stop(signal) becomes dispose(signal), and active work observes lifetimeSignal. The former private requiredTerminalFacade/requiredTerminalService fields are rejected; bundled features use typed capabilities instead.

Browser activation pluginId is the stable package/source id on every machine and matches workspace.provider.pluginId. Use host-unique runtimePluginId only for qualified contribution references. The only supported package entrypoints are @jmfederico/pi-web/plugin-api and @jmfederico/pi-web/server-plugin-api. The browser entrypoint is type-only; the server entrypoint exports types plus the three documented PI_WEB_HOST_*_CAPABILITY runtime tokens. The former plugin-api/unstable path and private dist/** imports are not contracts.

A server activation may feature-detect context.notices?.version === 1 and record a bounded info, warning, or error notice. Explicit scope ids alone control global/project/workspace/session visibility. The reporter remains live through dependent shutdown work, then is revoked immediately before that plugin's rollback or dispose(). See the full notice limits and lifecycle contract.

Browser and server module paths must use canonical package-relative form; empty or . segments, traversal, backslashes, and absolute or Windows drive-qualified paths are rejected. Each browser entry must declare a safe package-relative browserRoot containing its module; server-only entries must not declare one. The exact id pi-web and every pi-web.* id are reserved for PI WEB-owned bundled plugins; external declarations are rejected. Existing core, themes, and machine.* namespaces remain host-reserved.

  • Only files logically and canonically inside browserRoot are served; everything else in the package stays outside plugin asset routes.
  • browserRoot: "." makes almost the whole scanned package browser-public, so prefer a narrow build directory and put no secrets inside it.
  • The package-wide scan allows at most 4,096 entries and 16 MiB of file content, excluding traversal into .git and node_modules; files outside the browser root still count.
  • Both .js and .mjs are served with executable JavaScript MIME types. Prefer module-relative asset URLs for federation and nested deployments.
  • Treat browserRoot as the complete distributable browser graph: bundle or emit every runtime dependency, style, chunk, and asset inside it, with no bare package imports or private PI WEB source/dist/** imports.

Workspace files, navigation, and invalidation

Browser API v4 retains workspace-files capability v1, contribution navigation v1, and scoped invalidation. The five-operation WorkspaceFiles/WorkspacePanelFiles base remains implementable; callback contexts use WorkspaceFilesContextValue. Check context.files.capabilityVersion === 1 before using added methods, and treat optional context.navigation and the second onInvalidate argument as feature-detected.

  • The host binds file helpers to the callback's selected machine and workspace. Capability v1 adds cancellable reads/listings, the workspace-effective upload folder and preview limit, plus browser-ready preview/download URLs with routing already applied exactly once.
  • uploadFile() starts one cancellable browser-file transport with progress. It defaults to creating directories without overwriting, rejects cancellation as AbortError, and leaves multi-file batches and UI state to the plugin.
  • Optional panel navigation owns bounded namespaced deep-link state and browser history for one contribution; malformed restored state is ignored, and invalid or over-limit set() calls fail before changing the URL. During host-controlled route restoration, an exact target-identity snapshot may be supplied before URL publication, while writes remain fenced to the live address-bar identity. Navigation v1 set() returns no portable acknowledgement; read current callback snapshots rather than inferring acceptance from its result. See the full contract for the bundled Terminal's private host feedback and mixed-version gateway limitation.
  • Panels declare workspace.files to receive scoped successful-mutation and completed-agent-activity invalidations.

See the full workspace-files, navigation, and invalidation contracts in the Markdown API reference.

Host capabilities, package peer, and workspace providers

Plugin data directory

Server activation receives an absolute dataDirectory path, created before activation at $PI_WEB_DATA_DIR/plugin-data/<plugin-id> (default ~/.pi-web/plugin-data/<plugin-id>), for persistent plugin-owned files, subfolders, or databases on the machine running the plugin. It is separate from installed code and stable across package updates and session-daemon restarts. The directory is scoped by plugin id, not by project or workspace. Plugins own their storage format, safe writes, concurrency, migrations, and cleanup; PI WEB supplies no read/write/clear API or JSON size limit. This is a location convention, not a sandbox. The activation settings value contains only that plugin's settings, not the full PI WEB configuration. See the directory example.

Host-governed server capabilities

Server plugins import exact frozen tokens from @jmfederico/pi-web/server-plugin-api, list them in requires, and resolve them in start(). These capabilities provide current workspace resolution, hosted conversation creation, and messaging with Pi companions. File storage uses the activation context's dataDirectory path instead of a storage capability; plugins manage their own files.

PI_WEB_HOST_WORKSPACES_CAPABILITY resolves only opaque { projectId, workspaceId }. Every call reloads the project and reruns current provider arbitration, then returns a detached frozen project/workspace projection. Stale, missing, mismatched, and cross-project selections reject. Provider-private data and callbacks never escape; workspace ownership is authorization/topology metadata, not an implicit transport target.

PI_WEB_HOST_PI_SESSIONS_CAPABILITY offers run() with current project/workspace ids (at most 512 characters each) and one non-empty initial prompt (at most 64 KiB UTF-8). It re-resolves workspace authority and returns only a frozen session id plus a completion promise for completed, cancelled, or failed (failure text is bounded to 4 KiB). Completion describes the initial submission, including final provider errors; handled input can complete without an assistant response. PI WEB observes extension startup activity, announces the visible session before its initial prompt, and disables delegation tools. It exposes no model/path controls, runtime object, arbitrary session API, or per-run cancellation handle. The hosted conversation remains available for user work after initial completion or plugin disposal.

Use piSessions.create({ projectId, workspaceId }) to create without an initial prompt. It accepts only those two non-empty ids (at most 512 characters each) and returns frozen { sessionId } after native extension startup and normal UI publication, with no completion promise or messaging connection. PI WEB observes before extension startup. Then connect separately, subscribe to replies, and emit your companion's kickoff request. Have the companion wait for that request; creation does not suppress work an extension starts itself. Use native Pi APIs for agent behavior. Declare both capabilities in requires and resolve them in start().

Both creation methods use the same workspace authority and non-delegating hosted startup. They share four admission slots per plugin: create() releases its slot when startup/publication settles; run() holds it until initial completion. Published conversations are not capped by this quota. Startup failures reject. Plugin revocation cancels unpublished startup, including startup dialogs, but never reclaims a published conversation or later user work; browser disconnection does not stop it. Older v1 hosts without creation support reject create() with an update-host error; run() remains usable.

Hosted Pi package messaging v1

Declare PI_WEB_HOST_PI_SESSION_EVENTS_CAPABILITY in the backend's requires and resolve it in start(). This separate pi-web.host/pi-session-events v1 capability offers connect({ projectId, workspaceId, sessionId }). It re-resolves workspace authority and selects one exact, full session id already hosted in that workspace on this daemon, including existing UI sessions and launcher-created sessions. Sessions still initializing extensions reject. It does not create or open sessions or adopt independent runtimes. Use context.peer to reach the backend on the browser's selected machine. Creation is separate; run() has already submitted its initial prompt when it returns.

The connection offers on(channel, handler) (returns unsubscribe), emit(channel, data), close(), and a lifetime signal. The companion uses native pi.events.on and pi.events.emit, loaded through normal Pi package enablement and project trust. Register companion handlers during loading and initialize session state in session_start. Subscribe before emitting: replies can be synchronous. Values are native in-process data, not cloned JSON. Authors choose package-specific channels, payloads, correlation, acknowledgements, and error replies. Emit neither awaits async handlers nor confirms companion presence or agent completion; Pi logs listener errors. Startup emissions are not buffered or replayed.

Explicit close, plugin disposal, and hosted session close/replacement detach listeners and abort the connection signal. Later on() and emit() throw; close and unsubscribe are idempotent. Closing a connection never stops the conversation or its agent work. Browser disconnection alone does not close a backend-owned connection; authors can tie it to a peer channel when desired. Same-session /reload preserves the host connection while replacing companion handlers; runtime restart/reopen requires an explicit new connection even with the same session id. Use Pi's own agent APIs in the companion: supported native activity appears in the normal PI WEB conversation and running status without author reports. This is trusted-author tooling, not sandboxing: authors own message meanings and deliberately incompatible behavior outside the supported hosting lifecycle.

These values are created separately for each declaring plugin and revoked with its lifetime. Revocation rejects new work and cancels unpublished startup, including pending startup dialogs. Cleanup waits for startup to settle, not for published conversations, and does not abort later user work. State is available in the early phase; workspace, Pi-session, and session-messaging authority become active together only after provider topology and host session ownership exist. A plugin contributing a workspace provider cannot require any of these late capabilities because that is a topology cycle. In bundled-only safe start, external plugins never receive capabilities; none imports no server plugins while the kernel folder workspace and recovery/diagnostic surfaces remain available.

Try the companion/backend example

The Workspace Reviews example replaces the greeting demo with an opt-in Pi package; it is not installed by default. Start review reviews uncommitted changes in a dedicated conversation; Refresh reviews, a selector, and previous/next buttons browse saved plain-text findings. The panel uses selected-machine context.peer; the backend derives workspace authority from the host-resolved request, not browser-supplied paths or session ids.

Enable both halves on the target machine. PI WEB loads the piWeb browser/backend entries; Pi loads the companion through the package's pi.extensions manifest field. Add the absolute package directory to packages in the Pi profile's settings.json, preserving other entries and resource filters. Use sessiond's Pi profile, not an unrelated terminal profile. A PI WEB plugin link alone does not enable the companion. Project-local configuration needs normal trust. Manually restart sessiond when safe to activate the backend (this can interrupt sessions), then reload the browser. Use /reload in an existing hosted session after enabling the companion.

The backend declares both session capabilities, creates a conversation, connects separately, and subscribes before emitting a correlated request. The companion uses native pi.sendUserMessage, message/tool hooks, and agent_settled to capture final text. Receipt is not completion. Provider errors, aborts, failed tools, interfering prompts, and empty/truncated responses fail conservatively. Model credentials are required. Review instructions request no modifications but are not a tool sandbox.

Admitted reviews belong to the backend lifetime, independently of browser requests. Receipt waits are bounded to five seconds and completion to ten minutes. Cleanup closes capture, not agent work; inspect Sessions before retrying a timeout. Workspace-scoped plugin-owned JSON files in dataDirectory store status and findings through atomic replacement. Refresh loads metadata and one selected text record; stale running records after restart display as interrupted, never successful. There is no automatic retry, event replay, durable job recovery, retention policy, or pagination. See the full author guidance and example usage guide.

Exact-package peer

ServerPluginActivation.peer implements requests, channels, or both; browser panels and labels receive optional context.peer for their same package and exact active revision. Check peer.request and peer.openChannel directly. A peer does not need to own the addressed workspace. It receives cloned, frozen current project/workspace data, bounded JSON, and scoped cancellation, never provider-private data. Request input is limited to 256 KiB, output to 8 MiB, plugin callbacks to 10 seconds, sessiond dispatch to 25 seconds, and federation to 30 seconds.

For channels, the host supplies frozen scope, bounded open input, a channel-lifetime signal, and bounded synchronous send(); the plugin returns receive(), optional closed, and optional once-only close(). Data frames are limited to 64 KiB JSON and each physical hop queues at most 128 frames per direction, with 1 MiB browser-to-server and 1.25 MiB server-to-browser byte bounds. Edge processes admit 128 physically alive channels; sessiond separately admits 128 total, 32 per plugin, and 8 per plugin/workspace. Connect/open/receive/close/drain work is bounded, physical teardown is limited to 1 second, and channels expire after 12 hours with no idle timeout. A successful send() means queue acceptance, not delivery; continuity-sensitive plugins own reconnect and replay. Failures close both directions and release accounting only after teardown.

Workspace provider

Sessiond remains the single workspace-provider authority. An enabled server entry can contribute at most one provider. Primary providers probe first; bundled Git probes only as a fallback. Exactly one claimant owns the project's workspace semantics. Multiple claimants in the winning tier produce a visible conflict, and if nobody claims the kernel project-folder workspace remains available.

A provider returns stable workspace keys, accessible absolute directories, labels, exactly one main workspace, optional private JSON data, browser-visible publicMetadata, and optional removal presentation. Private data is returned only to provider-owned callbacks such as prepareRemove(); it is not peer transport. Public metadata is visible to all browser code and API consumers, so it must never contain secrets. capabilities.remove is true only for a workspace that advertises removal and whose owner implements it.

A removal plan approves a visible host-owned terminal run; it does not mean removal has completed. Its command is shell source interpreted by the host's login shell from a safe non-target working directory. Providers must use and shell-quote the supplied absolute workspace path, keep the operation in the foreground, and treat shell exit 0 as successful completion. Package protocols belong on the peer, not WorkspaceProvider.request().

PI WEB ships only bundled Git as a production provider. Third parties own replacement integrations such as Jujutsu providers. An installed primary provider can claim its projects and suppress fallback Git without PI WEB core changes; no reference replacement is shipped or promised here. Read the complete capability, peer, provider, quota, revocation, and cleanup contracts in the Markdown reference.

Built-in plugins

PI WEB ships core, discoverable plugins in the main @jmfederico/pi-web npm package. No separate pi install step is required. After updating PI WEB, restart sessiond so bundled server entries use the installed revision, then reload the browser. Browser-only bundled entries need only the page reload.

Built-in plugins can be managed from Settings → PI WEB plugins or with the top-level plugins config key. Settings labels required entries separately and does not offer an enablement toggle for them.

Terminal

Plugin id: pi-web.terminal. Terminal is the required bundled, machine-specific browser/server plugin. It supplies the Terminal panel and navigation action, Xterm UI and browser state, PTY/replay and command-run service, and its package-peer request/channel protocol. Normal and bundled-only startup activates it before ordinary plugins and publishes its browser entry only while the matching bundled server entry is active, healthy, revision-matched, and supplies both peer methods. The browser entry uses context.peer for local and selected remote machines, including selection, reconnect/replay, mobile keys, copy behavior, command-run display, and cleanup, instead of calling Terminal-specific application routes.

Terminal's former activation-only requiredTerminalFacade and requiredTerminalService fields were private composition escape hatches. Browser API v4 and server API v3 reject them. Bundled Terminal now uses the same typed capability mechanism available to third-party plugins, and its browser/server protocol uses public context.peer and ServerPluginActivation.peer.

Ordinary config, Settings, and pi-web plugins disable pi-web.terminal cannot disable Terminal. Canonical contribution ids use pi-web.terminal:*; the released core:workspace.terminal and core:view.terminal aliases remain supported. Missing, incompatible, failed, or unhealthy startup reports the failure instead of claiming Terminal is available. Only an active session-daemon lifecycle snapshot can declare intentional no-Terminal recovery; unavailable or incompatible runtime state withholds ordinary plugin modules and remains retryable. For recovery, run pi-web plugins safe-start set none --restart; diagnosis and Settings remain available without Terminal, then clear safe start after repairing the installation.

Files

Files is a normal browser-only bundled plugin that supplies the Files workspace panel, viewers, uploads, and its navigation/refresh actions through browser API v4. It is enabled by default. Disable files in Settings or config, then reload the page; no session-daemon restart is required.

Disable Files 
{
  "plugins": {
    "files": { "enabled": false }
  }
}

Disabling Files removes its product panel and actions, but not the mandatory host workspace-file access used by attachments and other plugins. Chat and other available workspace panels remain usable, and PI WEB selects an available panel generically. Legacy files / core:workspace.files routes, query state, and saved shortcuts continue through aliases.

Git

Git is enabled by default and is PI WEB's bundled fallback workspace provider. It discovers worktrees, owns Git removal plans, serves status/diff through its package peer, and adds the Git panel. An enabled primary third-party provider can claim a project before Git. Disabling git and restarting sessiond leaves the kernel folder workspace plus generic Files, Terminal, and Session features; reload the browser so Git contributions disappear.

Updates

Updates adds a conditional Updates workspace tab with PI WEB update, restart, and installed-service guidance, plus a Check for PI WEB Updates action. It is built into PI WEB, enabled by default, and uses the selected machine's plugin copy when machine federation is active.

  • Plugin id: updates
  • Selected-machine status refreshes every 15 minutes while a browser tab is connected.
  • Automatic npm release lookups are cached for six hours; the action bypasses the caches and checks immediately.

Manage PI WEB plugins

Settings → PI WEB plugins compares desired package/config state with the active sessiond startup snapshot on the selected machine. It reports browser-only, active, failed, incompatible, disabled, not-active, unknown, conflict, stale-revision, health, safe-mode, and restart-required states. Settings values remain private; diagnostics expose only revisions and fingerprints.

Package installation stays under Settings → Pi packages. Plugin enablement writes the selected machine's top-level plugins config key and remains editable while sessiond is unavailable, although active state cannot then be verified.

Plugin config shape 
{
  "plugins": {
    "git": { "enabled": true, "settings": {} },
    "info": { "enabled": false }
  }
}

Plugins default to enabled. A browser-only change applies after a page reload. A server entry captures enablement and JSON settings only at sessiond startup; replacing package files or saving config changes desired state without hot-reloading the active provider registry.

Lifecycle, restart, and offline recovery

  1. Install or update the plugin package on the target machine.
  2. Set its desired enablement/settings.
  3. For a browser-only plugin, reload the browser tab.
  4. For a server-backed plugin, restart sessiond, wait for it, then reload the browser tab.
Manual session-daemon restart: for the native systemd user service, run systemctl --user restart pi-web-sessiond (unit pi-web-sessiond.service). Restarting sessiond may interrupt active sessions and runtime ownership. Web/UI autoreload, restarting only web/API, browser reload, and Pi's /reload do not activate server-plugin changes.

Offline recovery edits config without contacting sessiond, discovering packages, or importing plugin code. Run these commands on the affected target machine; add --config /path/to/config.json when its services use a custom config.

Server-plugin recovery 
$ pi-web plugins disable <plugin-id> --restart
$ pi-web plugins safe-start show
$ pi-web plugins safe-start set bundled-only --restart
$ pi-web plugins safe-start set none --restart
$ pi-web plugins safe-start clear --restart
  • disable persists plugins.<id>.enabled: false while preserving unrelated config. It rejects required pi-web.terminal; use no-plugin safe start only for recovery.
  • bundled-only filters discovery before external server packages are considered, while the bundled Terminal entry remains required.
  • none imports no server plugins. The kernel folder workspace and diagnosis/Settings surfaces remain available, but Terminal and Terminal-backed command workflows do not.
  • clear restores ordinary configured discovery on the next start.
  • An unsupported serverPlugins.safeStart shape or value fails closed as effective none; use show, then set or clear, to repair it offline.
  • --restart acts automatically only for a recognized safe installation; otherwise PI WEB prints manual guidance. Config is durable before the restart attempt, so restart manually if that attempt fails.

Ordinary plugin failures are attributed and quarantined when the host can catch them. Safe start remains necessary because trusted in-process code can block or terminate sessiond. Every restart can interrupt active sessions/runtime ownership.

Remote machine plugins

With machine federation, the gateway loads compatible browser entries from the selected remote machine while server entries stay in that target's sessiond. Actions, panels, labels, file/terminal helpers, and exact-package context.peer requests/channels all follow the selected machine. Activation pluginId, peer identity, capability ownership, and workspace-provider ownership keep the stable source id; runtimePluginId may be machine-scoped so qualified contributions remain host-unique.

  • Peer requests and channels carry the source plugin id and active target revision through bounded gateway transports; workspace ownership remains metadata rather than a transport target.
  • Server-backed browser code is served only for an exact active package/source/scope/settings/revision pairing.
  • machineSpecific decides whether a browser-only gateway copy is portable; dual entries are always machine-specific.
  • Remote theme contributions remain ignored because themes are app-wide.
  • A current gateway reports missing or unsupported lifecycle/peer capabilities explicitly instead of falling back to gateway code.

Mixed-version provider/plugin operation is not supported in either upgrade order. A newer gateway rejects an older target's entire remote plugin manifest when it lacks the lifecycle contract, so that target's browser-only contributions and Git panel are unavailable. An older gateway still calls legacy core Git routes removed by an updated target, so remote Git status/diff returns 404. Upgrade the gateway and target together, restart their updated web/API processes and the target session daemon, then reload the gateway page. Other machine features use their own capability negotiation.

Select the remote machine in Settings → PI WEB plugins to edit desired state; the panel requires the target machine's plugin lifecycle support. Restart that remote session daemon for a server-backed change, then reload the gateway page.

Current manifests publish leading application-root module references. The browser keeps them inside the current application base, and the gateway rewrites accepted remote references for root and canonical trailing-slash nested deployments. Prefer module-relative assets such as new URL("./asset.json", import.meta.url); hard-coded /pi-web-plugins/<original-id>/... paths can point at the gateway copy.

Production usage

Local plugins work with the production native-service install. Put each package under ~/.pi-web/plugins/<plugin-id>/, or symlink it there while developing. No PI WEB rebuild is required. Browser-only entries need a page reload; server-backed entries need a sessiond restart followed by the page reload.

If PI_WEB_DATA_DIR is set, use $PI_WEB_DATA_DIR/plugins instead of ~/.pi-web/plugins.
Install a local plugin folder 
$ mkdir -p ~/.pi-web/plugins
$ ln -s /path/to/plugin-folder ~/.pi-web/plugins/plugin-id

AI-friendly docs

The full plugin reference is available as Markdown for AI agents to read, fetch, and follow: plugins.md.

If you want to understand the API yourself, ask an agent to read that file and explain the relevant public extension points for the plugin you want. Browser private routes/runtime fields, source internals, and dist/** declarations are not stable APIs. Use only the two documented package entrypoints; the server entrypoint's three host-capability tokens are its only public runtime values.

Develop and debug

  • Keep the source folder outside ~/.pi-web/plugins and symlink it in.
  • Build entry JavaScript at the exact package-relative paths declared in metadata, and keep the browser module/assets inside a narrow declared browserRoot.
  • Declare "type": "module" for a .js server entry or emit .mjs.
  • After browser-only edits, reload or hard-reload the tab and check its console.
  • After server edits, restart sessiond, reload the tab, and inspect pi-web logs.
  • Use Settings → PI WEB plugins for desired/active, health, conflict, and revision diagnostics.

$ curl http://127.0.0.1:8504/pi-web-plugins/manifest.json

Trust model

Plugins are not sandboxed. Browser entries can use browser APIs, read/write workspace files through helpers, start terminal commands, and render arbitrary UI. Server entries execute in-process inside sessiond with the service user's filesystem, environment, and process permissions, and share sessiond's event loop. Install only packages you trust.

Ordinary import/lifecycle/health failures are quarantined when PI WEB can catch them, but server plugins are not crash-isolated. A CPU-bound, blocking, or deadlocked callback can stall sessions, terminals, and health endpoints. Abort signals and deadlines bound only cooperative asynchronous code and cannot preempt code that ignores them. This is a stability boundary, not a security boundary; offline disable and both safe-start levels are the recovery path.
