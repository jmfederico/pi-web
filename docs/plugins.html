Build workflows around Pi and your sessions

A plugin can add a web interface, run backend work, or combine both.

  • Add web tools — panels, controls, and views in PI WEB.
  • Customize transcript views — tool results, including built-in tools, and displayed custom messages.
  • Run backend work — tasks, integrations, and background processes.
  • Connect them — trigger work from the UI and bring progress and results back.

For example, build a review panel that starts a Pi conversation and brings its findings back for you to inspect. Browse community plugins for more ideas.

Build your own

[Describe your plugin]

Install and manage

  1. Open Settings → Pi packages and install the package by its npm name, git/URL, or local source.
  2. Open Settings → PI WEB plugins to check its status and enable or disable its web integration.
  3. Follow the reload or restart guidance shown there.

Browser-only changes need a page reload. By default, server-backed changes need a restart of the target session daemon, then a page reload. A daemon restart can interrupt active sessions and terminals. Check active work first. Reloading the page or using Pi's /reload does not activate server-plugin changes.

For local development, npm run dev:web defaults PI_WEB_DEV_PLUGIN_PAIRING to 1: rebuilt plugin UI can use the running old backend after a browser refresh, without plugin changes. Production stays strict by default. Set PI_WEB_DEV_PLUGIN_PAIRING=0 before launching to test strict pairing. The flag accepts 1/true and 0/false (case-insensitive); invalid values fail web/API startup. Existing update-pending notices remain in Settings. Changed request/response formats may cause runtime errors in development; backend changes still need a daemon restart.

Relays, Workflows, Session naming, and MCP manager ship with PI WEB and are automatically provisioned once per agent profile. At session-daemon startup, configured copies follow the running PI WEB installation while preserving resource filters. Once provisioning is recorded, removal through Settings → Pi packages, pi remove, or manual package-settings edits persists across daemon restarts. Reinstall explicitly from Available packages if you change your mind; reinstalling does not reset the record.

PI WEB stores provisioning records in $PI_WEB_DATA_DIR/pi-package-provisioning.json. Existing dismissals migrate with their original timestamps and remain honored; configured packages are recorded at startup, and new installs are recorded only after success so failures can retry. Upgrade caveat: older CLI or manual removals without a record can receive one last automatic reinstall. Remove the package again afterward to keep it absent. See one-time package provisioning for ledger and migration details.

MCP manager

The bundled @jmfederico/pi-mcp-manager package (pi-packages/mcp-manager) provides the MCP tab through plugin ID mcp-manager. It is enabled by default and follows the selected machine. Its thin Pi extension loads configured servers in standalone Pi TUI sessions and PI WEB without a web runtime dependency. Management controls exist only in the web plugin; the package adds no TUI management commands.

The package follows the one-time provisioning rules above. Remove it through Settings → Pi packages and reload idle sessions to stop loading its servers; reinstall from Available packages to restore it. Disabling only the PI WEB plugin hides management while the installed extension continues loading servers. Native Pi MCP configuration and authentication remain Pi-owned. See managed MCP configuration for package-owned files, environment enforcement, trust, and manual migration.

The bundled Session naming Pi extension (@jmfederico/pi-session-naming) names each new conversation from its first prompt in PI WEB and the TUI. Remove it through Settings → Pi packages to use another naming extension; reinstall it from Available packages to restore naming. See Session naming configuration for model, token-budget, thinking-level, and timeout settings, plus migration from the old core settings.

Scheduled agent tasks (beta) is a shipped optional package for agent-managed schedules and a read-only Scheduled tasks dashboard. Install it from Available packages; its web plugin is disabled by default. See its guide for timezone settings, activation, and execution history. It is separate from Workspace Tasks' terminal command buttons.

Packages, extensions, and plugins

A Pi package is an installable bundle. A Pi extension changes agent behavior; a PI WEB plugin adds web tools. One package can include both. Disabling its web plugin leaves its extensions, skills, and prompts available.

Plugin configuration

Server plugins receive resolved settings from PI WEB without reading config files or parsing environment variables themselves. No settings UI is required; plugins validate their own values. Settings currently edits enablement, not arbitrary plugin settings. See the plugin configuration contract for delivery, project overrides, and browser-only limitations. Generic settings are not a secret store.

Remote machines

Installation and settings apply to the machine selected in Settings. A remote plugin runs its server work there and shows its UI in your browser. Keep gateway and remote PI WEB versions compatible.

Trust and recovery

Install only plugins you trust. Plugins are not sandboxed: they can run code in your browser or access files, environment variables, and processes on their machine. Faulty server plugins can affect other sessions.

Model-backed features may send data to a model provider. Check the plugin's description before using it with sensitive content.

If a plugin fails, check its status in Settings → PI WEB plugins on the affected machine. Disable it there if needed. If the UI cannot recover, use the offline disable and safe-start commands.

For agents and developers

The plugin implementation reference is the starting point for APIs, packaging, examples, compatibility, and lifecycle rules.

Server plugins can declare PI_WEB_HOST_SESSION_STATE_CAPABILITY (pi-web.host/session-state v1) from @jmfederico/pi-web/server-plugin-api for private, revision-checked conversation state. Reads return a value and revision (absent state uses ""); writes require that revision, reject archived sessions, and report stale writes as SESSION_STATE_CONFLICT. State is bounded to 64 KiB and 64 JSON nesting levels. Opt-in inheritance copies the latest state before a fork or spawned session's first prompt; opting out excludes active state, not transcript history. This is separate from public metadata, not a secrecy boundary. See private session state for signatures, saved-session hosting, native persistence, and the reset-aware readSessionState helper.

PI_WEB_HOST_PROJECT_TRUST_CAPABILITY (pi-web.host/project-trust v1), exported by the same server API, provides get({ projectId, workspaceId }) for explicit saved/default Pi trust, excluding empty-workspace auto-trust. Both capabilities use normal declaration, authority, and revocation rules and are not MCP-specific. Newly installed capability code needs a target session-daemon reload; restarting interrupts active sessions and terminals. See explicit project trust.

Theme-only packages declare themes and light/dark pairs in package metadata and ship CSS and assets without browser JavaScript or a server module. The default palette can load alongside the application while a loading screen is visible. Declarative themes can contribute loading-screen colours before JavaScript runs; General settings fetch the full inventory once per dialog, with explicit retry on failure and HTTP caching. Existing runtime theme contributions remain supported with a deprecation warning; built-in themes:* IDs and saved choices are preserved. See theme authoring and migration.

Files and Git share locally bundled Material file-type shapes in one muted grey that follows the active colour theme. Git retains separate filename colours and status labels for changes. Choose an independent icon theme in Settings → General → File icons. Plugins can contribute complete icon sets; see file icon themes.

Browser v5 plugins can render tool entries and displayed custom messages inside the core transcript frame, with a default-view control and the existing view as fallback. Rendering changes presentation, not tool execution; hidden messages remain hidden.

Tool contributions use { id, target: "tool", resolve(toolName, next) }: the first resolver in discovery order gets first refusal and can delegate, replace, or wrap a downstream renderer. There is no declarative tool-name field. next() returns renderer callbacks, not HTML. The web transcript supplies its core default renderer at the end of the chain, allowing wrappers to decorate normal tool cards too; unchanged delegation to that default keeps the normal view without a custom-view toggle. The resolver type permits undefined in contexts without a supplied default. Returning undefined ends selection and uses the core fallback without trying later resolvers. A selected renderer’s render can also return undefined to use that fallback without restarting selection.

Custom messages retain { id, target: "custom-message", customType, render }: the first eligible exact match wins, with no next callback or retry after decline. The pi-web/transcript-rendering@1 capability identifies support. See the transcript renderer contract for exact targets, synchronous rendering, selection, cancellation, and theme integration.

Browser v5 plugins can add Markdown syntax shared by chat and host-rendered documents, including Files previews. The pi-web/markdown-rendering@1 capability lets plugin views use that engine and its code-fence previews. Document views escape source HTML, omit images, and allow safe external links; chat retains its own link and image policy. See the Markdown API guide for synchronous syntax callbacks and presentation sanitization. Browser-only syntax plugins need no session-daemon restart.

Plugins can add file-type views directly to Files, including binary formats. The bundled Audio previewer demonstrates playback and seeking. See file previewers.

Plugins can pin, unpin, archive, restore, and explicitly delete archived sessions through the host's session lifecycle service. Pins protect cleanup, not deliberate plugin commands. Existing pins are preserved during a coordinated pin-storage upgrade.

Plugins can deliver generated documents, media, and other binary data through scoped backend resource URLs, without exposing a separate server port. See binary resources and media delivery.
