Highest priority first: enforced environment → browser-local choice (where applicable) → supported project override → writable machine config → deployment defaults → built-in defaults.

Without a deployment file, existing writable config behavior is unchanged. A missing writable file means no saved overrides. Deployment defaults supply starting values, not locks; use environment policy to enforce values. Mount deployment defaults read-only and keep PI_WEB_CONFIG writable; it must not select the defaults file.

Each declared setting replaces its lower-layer value; there is no general recursive merge. The schema declares these independent namespace leaves: uploads.defaultFolder, attachments.defaultFolder, sessionNaming.model, .maxTokens, .thinkingLevel, .timeoutMs, sessionArchive.directory, pathAccess.allowedPaths, and defaultLocalization.language, .formatLocale, .timeZone, .hourCycle. Leaves inherit independently across deployment defaults, writable config, applicable project config, and environment policy. Empty namespaces {} contribute no overrides; missing leaves inherit.

Each plugin’s enabled and each top-level plugin setting also resolve independently. Individual array/dictionary-valued settings replace entirely, including explicit empty values. defaultTheme remains one atomic, coherent preference; shortcuts and deprecated agent are also atomic. JSON depth alone does not define a setting.

Sources, saves, resets, and the config API

Settings shows inherited sources and environment policy; enforced controls are read-only. Where a saved override has a Reset saved override control, it deletes the override to expose the next applicable layer, rather than saving today’s default. Loading deployment defaults keeps them separate from writable overrides. Enforced theme/localization temporarily masks browser choices without erasing them; removing policy restores those choices.

Config responses include config (writable overrides), effectiveConfig, optional defaultsPath/defaultsConfig, configSources (JSON pointers mapped to defaults, config, or an environment variable), and enforcedSettings (pointers mapped to environment variables). Source and enforcement pointers address declared leaves, such as /sessionNaming/model and /pathAccess/allowedPaths; the archive alias reports /sessionArchive/directory. Missing sources inherit built-in/feature defaults. This metadata describes the machine, not browser/project provenance.

Use PATCH /api/config, or PATCH /api/machines/<machineId>/config for selected-machine-supported keys (local selects the gateway machine). Both accept optional config-shaped set and JSON-pointer array unset:

{
  "set": { "quietMode": true },
  "unset": ["/defaultTheme", "/defaultLocalization/timeZone", "/plugins/git/settings/workspaceDiscoveryHooks"]
}

unset accepts known leaf pointers such as /sessionNaming/model, /uploads/defaultFolder, and /pathAccess/allowedPaths, as well as container resets such as /sessionNaming. Atomic settings reset at their top-level pointer, such as /defaultTheme. UI container-group resets remove only unlocked saved leaves in one request. An API container reset overlapping any enforced leaf is rejected, preserving saved choices hidden by enforcement. In pointer segments, escape ~ as ~0 and / as ~1: setting a/b~c uses /plugins/git/settings/a~1b~0c. Conflicting set/unset targets and enforced changes are rejected. There is no null reset sentinel: null keeps its schema meaning, such as disabling a shortcut. Existing PUT endpoints retain replacement semantics for unenforced settings. Omitted enforced settings preserve their hidden saved values; explicitly changing an enforced saved value is rejected, while unchanged values may round-trip. A legacy save cannot create a saved override for an enforced setting when none exists. Federated protection requires enforcement metadata from the target; upgrade older peers before relying on it.

Custom config paths: service commands and recovery

start, restart, and doctor use the config path saved in the installed services for readiness checks unless the caller supplies a nonempty PI_WEB_CONFIG override. doctor checks the managed setup, not every custom runtime environment.

UI & new-session defaults

Machine name

Set installationName in the machine’s config, enforce it with PI_WEB_INSTALLATION_NAME, or edit Settings → General → Machine name for the selected machine. Names are trimmed and limited to 120 characters without control characters. An empty or unset name uses PI-WEB. This machine-global setting needs no restart; reload other windows to refresh their labels.

{ "installationName": "Build lab" }

The name replaces the local machine label and remains visible with one machine in browsers and installed PWAs. Federated machines use their reported name unless you set a Local display name; clear that field to use the remote machine's name again. Existing registry names remain overrides. Unavailable or older remotes without a reported name use PI-WEB; discovered names are retained during the gateway process lifetime.

The PWA manifest uses the gateway name, with (dev) appended for development deployments. Selecting a remote does not rename the installed gateway app. Browsers decide when existing launcher names update; reinstall the PWA if the old name remains.

Use the selectors in chat, Settings → General → Theme, or Settings → Keyboard. Pi defaults and PI WEB UI settings live in different configuration files.

Settings → General → File icons independently selects an icon set for Files and Git in this browser. Git keeps filename colours and status labels separate from icon artwork. Material file-type shapes are bundled locally by default and rendered in one muted grey supplied by the active colour theme. Choose generic file icons or reset to Material. Missing sets fall back without erasing your choice. This browser-only preference has no gateway default, project setting, or environment override. See file icon themes for plugin contributions.

Default selection and shortcut rules
  • Model/thinking stars change new-session defaults, not the current session. Resumed sessions keep saved choices.
  • Project Pi settings, explicit startup choices, and per-model thinking settings can override defaults. If the default model is disabled, startup falls back to the first enabled model.
  • mod means Ctrl or ⌘. App shortcuts support sequences; composer send bindings support one combination only.
  • Unassigned Enter/Shift+Enter insert newlines; Enter accepts a selected completion first. null disables keyboard submission, not the send button.
  • Existing browser-local Enter preferences remain the fallback until a composer binding is configured. Reset restores that fallback.

App shortcuts do not start with unmodified or Shift-only keys while editing text. Avoid conflicting bindings and browser-reserved combinations. New bindings are saved in gateway config.

Theme defaults and device choices

In Settings → General → Theme, choose a theme and Auto mode, then:

  • Use on this device saves a choice for this browser only.
  • Set as default shares a default without replacing existing device choices.
  • Use the default clears this browser’s override.

Unless PI_WEB_DEFAULT_THEME enforces the theme, device choices take precedence over the configured default, then the built-in default (PI WEB Dark with Auto on). Enforcement locks theme controls and preserves the device choice for when policy is removed. Auto follows the device’s light/dark preference for paired themes; unpaired themes stay selected.

The initial page includes the gateway default's details and CSS, including associated pair details and both variants' CSS for Auto. Accepting that theme needs no additional theme request. If the default requires legacy browser activation, the backend supplies Classic while preserving the intended preference. The app appears with the delivered palette; the browser then requests another theme if its saved choice needs one, or applies a legacy theme when its plugin activates. A failed or unavailable choice leaves the current palette usable without erasing the saved choice. General settings load the complete inventory once per dialog, with explicit retry on failure and normal HTTP caching. The browser-native loading screen covers initial application startup, not later browser overrides.

Device choices keep the existing localStorage key pi-web-app-theme and { themeId, auto } format. Theme packages use declarative metadata and revision-qualified assets, not cached arbitrary CSS in localStorage or new config files. See theme packages for authoring and migration.

The default belongs to the gateway, not a project or remote machine. Changes apply after settings save or browser config refresh, with no service restart.

{ "defaultTheme": { "themeId": "themes:pi-web-dark", "auto": true } }

Use a theme contribution ID rather than a display name. Built-in IDs remain themes:pi-web-dark, themes:pi-web-light, themes:classic, themes:paper, and themes:graphite after migration to declarative packages.

Path formats, overwrite behavior, and folder rules
  • External roots: existing directories using absolute paths or ~, such as /opt/reference, ~/SDKs, or Windows absolute paths on Windows hosts. Relative roots are not supported; symlink escapes are rejected.
  • Upload/attachment folders: nonempty workspace-relative paths. Absolute paths and .. traversal are rejected.
  • Uploads: create parent folders; existing files are preserved unless overwrite is enabled in the review dialog. Direct drops never overwrite.
  • Upload dialog only: clear the destination field to upload that batch to the workspace root.
  • Attachments API: an explicit per-request folder overrides the configured default.

Session naming model and token budget

Use Settings → Session daemon → Session naming on the selected machine. The naming model button opens a searchable list of that machine’s available models; choose Use session model to remove the model override. No active session is required. Refresh settings to reload the list after configuring a provider. Naming defaults to the session’s model and 24 tokens, including for reasoning models. It does not change the conversation’s model.

{ "sessionNaming": { "model": "provider/model-id", "maxTokens": 2048, "thinkingLevel": "off", "timeoutMs": 90000 } }

All overrides are optional. Omit model to use the session model; omit maxTokens to restore 24. The model uses that machine’s catalog and configured credentials. The budget must be a positive integer; providers may count reasoning against it. It does not control title length.

thinkingLevel defaults to minimal. Supported values are off, minimal, low, medium, high, xhigh, and max. Choose off to disable optional reasoning where supported, while keeping a positive token budget for the title. Models and providers may limit or map levels; off cannot disable mandatory reasoning. Naming settings do not change the conversation’s thinking level.

timeoutMs sets the total naming-request timeout, including gateway queueing, model loading, and generation. It defaults to 10000 (10 seconds). Use a positive integer in milliseconds, up to 2147483647; Settings displays seconds. Increase it for local models that need time to load. Resetting the saved sessionNaming override restores inherited naming settings (10 seconds if no lower layer supplies a timeout). This is a total wall-time limit, not an idle timeout. Naming fields inherit independently; reset /sessionNaming/timeoutMs to restore only the inherited timeout, or /sessionNaming to remove the saved group when no field is enforced. PI_WEB_SESSION_NAMING enforces only supplied fields, so {"model":"provider/model-id"} leaves token budget, thinking level, and timeout independently configurable.

Saved model, budget, thinking-level, and timeout changes apply to the next naming request without a restart or reload. Existing names and in-progress naming requests are unchanged. Agent permission changes in the same panel still require a session-daemon restart. Naming failures use the first-message fallback and are recorded in daemon logs.

Independent sessions vs. tracked subsessions

Independent sessions run in a workspace of the same project without granting management rights or sending automatic lifecycle notices to the initiating session. Tracked subsessions run in the parent’s working directory and give the parent inspection and lifecycle controls. When a tracked child’s run ends, the parent receives an idle or error notice—not the child’s final answer or a claim that its task is complete. The parent can keep working or use yield_to_subsessions to wait for lifecycle notices. Received notices are not automatically repeated; explicit inspection remains available through check_subsession and read_subsession.

Both kinds of session use the same send_session_message tool for communication when messaging is enabled. What to communicate, when to reply, and whether a task is finished are decisions for the agents and their instructions, skills, or workflows.

Parents use manage_subsession with a direct child’s sessionId and an action: stop interrupts its current run, resume continues its conversation, and archive archives it. The optional prompt supplies new instructions for resume only; other actions reject it. Stop interrupts work rather than freezing a process or undoing changes; a later resume or message can start another run. Resume rejects a child that is already working. Archive requires the child to be idle; stop it first if needed. These controls do not extend to unrelated sessions or grandchildren.

sessionMessages controls whether sessions, including tracked children, receive send_session_message. It defaults to true, independently of the spawning flags. Set it to false or set PI_WEB_SESSION_MESSAGES=0 to remove the tool and block session-message delivery after restarting the session daemon. It sends a message to a known session ID in any workspace of the same registered project on the same machine. An idle recipient starts a turn; a busy recipient receives a queued follow-up. Sending creates no parent/child relationship, grants no inspection or control rights, and subscribes to no results. Messages include the runtime-provided sender session ID so recipients can reply. Children also receive their parent’s session ID in runtime context; neither identity implies additional permissions or a required collaboration workflow. The tool returns acceptance, not an answer or confirmation that the message was read. Queued messages use the runtime’s normal queue and are not a durable mailbox; stopping or closing the recipient can discard pending work. Archived sessions cannot receive messages.

Agent-created tracked subsessions are collapsed under their parent. Use Agent subsessions to expand them. User-created forks and clones, unknown-origin sessions, children without an available parent, and independent sessions remain visible.

New sessions inherit the parent’s model and thinking level unless another model is requested, for example with a #provider/model-id prompt reference. Thinking levels are limited to what the chosen model supports.

Question forms and extension dialogs are different

Agents can ask questions with choices or free-text answers. You may leave questions unanswered; partial submissions are confirmed before sending. Answering or skipping resumes the agent.

Forms are saved in the conversation and survive restarts. Only a form at the end of the active conversation is open; answering, skipping, or sending another message closes it. Earlier forms remain expandable for read-only review. Returning the conversation to a question reopens it; archived conversations remain read-only.

Extension dialogs are always supported, independently of askUser. The sooner of the extension’s timeout and the configured daemon timeout cancels an unanswered dialog.

Project plugin settings: scope, merge, and restarts

Supporting server plugins, including Git, accept plugins.<id>.settings in <project>/.pi-web/config.json at the registered project’s path, not in individual worktrees. Project top-level keys override global settings unless that key is enforced through PI_WEB_PLUGINS; nested objects are replaced rather than deep-merged. Plugin enablement stays global.

After changing global or project server-plugin settings, manually restart the target session daemon, then reload the browser. A browser reload, web/API restart, or Pi’s /reload is insufficient. The daemon restart can interrupt sessions and terminals; finish important work and restart from outside its hosted sessions.

Git worktree discovery hooks: opt out

plugins.git.settings.workspaceDiscoveryHooks enables automatic worktree discovery on supported Git builds (Git 2.54+). It defaults to true and preserves existing hooks. See Automatic Git worktree discovery.

To opt out, merge this into machine config or the registered project’s .pi-web/config.json:

Git hook opt-out
{
  "plugins": {
    "git": {
      "settings": {
        "workspaceDiscoveryHooks": false
      }
    }
  }
}

Project values override the machine default unless environment-enforced. Changes require a manual session-daemon restart. Disabling hooks leaves the Git plugin and ordinary workspace discovery available.

Git worktree discovery when running multiple instances

Most installations need no changes. Docker dev automatically uses dev to keep its worktree notifications separate from production; production keeps its existing behavior.

For a custom setup where instances share a PI WEB data directory, set PI_WEB_INSTANCE_NAMESPACE=dev in the dev session daemon’s environment and leave it unset in production. Use a different name for each additional instance: 1–32 letters, digits, underscores or hyphens, starting with a letter or digit.

Restart the affected daemon to apply the change; for Docker, recreate the affected containers. This interrupts active sessions and terminals, so finish important work first. This setting separates Git notifications only; separate data directories are still recommended for independent instances.

Keep the name stable. If you need to retire a name, disable discovery hooks while still using that name before switching, so the old notifications are removed.

Recover from a broken server plugin

Run on the affected machine. These commands edit config without loading plugin code. Add --config /path/to/config.json for a custom config.

Offline plugin recovery
Command Effect
pi-web plugins disable <plugin-id> --restart Persist disablement; rejects required Terminal.
pi-web plugins safe-start show Inspect safe-start state.
pi-web plugins safe-start set bundled-only --restart Skip external server packages; keep bundled plugins.
pi-web plugins safe-start set none --restart Skip all server plugins, including Terminal; keep diagnosis/Settings surfaces.
pi-web plugins safe-start clear --restart Restore normal configured discovery.

Restart caution: --restart acts only for a recognized safe installation and can interrupt sessions. Config is saved first; follow manual guidance if restart fails.

Server plugins are trusted in-process code, not crash-isolated. Plugin guide →

Fleet compatibility and unavailable plugin UI
  • Upgrade the gateway and target together; mixed-version plugin operation is unsupported.
  • Restart updated web/API processes and target sessiond, then reload the browser.
  • By default, a paired UI is withheld when its package/settings do not match running server code, or the server plugin is unhealthy/incompatible.
  • The npm run dev:web launcher defaults the process-only PI_WEB_DEV_PLUGIN_PAIRING flag to 1, allowing rebuilt plugin UI to use the running old backend. Set it to 0 for strict development pairing. It accepts 1/true and 0/false (case-insensitive); invalid values fail web/API startup. Other startup paths stay strict by default. Update-pending notices remain, and backend changes still need a daemon restart that can interrupt sessions and terminals. See plugin development and restart guidance.

Session archive directory: precedence and path rules

Set sessionArchive.directory in the global config file to choose where new session archives are written. It defaults to $PI_WEB_DATA_DIR/archived-sessions. Project-local overrides are not supported.

{ "sessionArchive": { "directory": "/srv/pi-web/archives" } }

PI_WEB_SESSION_ARCHIVE accepts a JSON object such as {"directory":"/srv/pi-web/archives"}. The nonempty PI_WEB_SESSION_ARCHIVE_DIR path alias wins over both JSON environment policy and config files; an empty alias is ignored. Relative paths resolve against the process working directory. Use an absolute path for a predictable destination; do not rely on tilde expansion.

Restart the session daemon on the affected machine after changing either value. Only the destination for new archives changes: the index stays at $PI_WEB_DATA_DIR/archived-sessions.json, existing records keep their stored paths, and no migration occurs. Edit the global config file or daemon environment directly.

Changing directories or running a second instance
  • State migration: a new PI WEB data directory starts with empty registries and no archive index. Changing paths does not migrate data; archive records retain their stored paths. See archive path rules.
  • Second instance: use a distinct data directory, daemon endpoint, and web port. One live session daemon owns each data directory.
  • Agent state: uses the bundled Pi SDK’s data layout. PI WEB does not convert profiles or move PI WEB-managed archives when the agent directory changes.
  • Active paths: changing Pi state or session paths requires a sessiond restart; web/API-only restarts do not apply it. Sessions, terminals, and package operations use the daemon’s active paths. If those paths are unavailable, profile-dependent operations are unavailable too.
Environment inherited by agent processes
  • Agent shells, terminals, and child sessions inherit the daemon environment, including its Pi state paths.
  • NODE_ENV and PORT are removed so they do not interfere with development commands.
  • PI_WEB_SESSION=1 marks nested processes. Inherited PI_WEB_* values still point to the hosting instance. Use a separate data directory, daemon endpoint, and web port for a second instance.
  • Do not restart the hosting session daemon from inside an active session you need to preserve.
  • environmentFacts includes nesting and deployment guidance in session system prompts by default. Set it to false, or use PI_WEB_ENVIRONMENT_FACTS=false, to omit that guidance. Restart sessiond after changing it.

MCP server sign-in and sign-out

Select a nonarchived session, then choose MCP login or MCP logout from Actions. Each action asks you to select an eligible server, even when only one is available. MCP actions are separate from model-provider authentication; the provider dialogs have no MCP footer.

Alternatively, open Settings → MCP to see enabled OAuth-eligible servers for the selected session on the settings machine. Each server has Login and Logout controls that target it directly, without another server picker. Disabled servers, servers using header-based authentication, and stdio servers are not listed as OAuth authentication candidates.

Both entry points use the same MCP dialog flow, showing the chosen server and Pi’s progress and outcome without switching to Chat. They require an idle session in a trusted workspace with Pi’s built-in MCP command enabled. Finish the current MCP authentication operation before starting another on the same machine.

Pi can reuse valid or refreshable credentials without asking you to authorize again. No browser prompt may mean credentials were reused; it is not proof of success. Read Pi’s messages for the outcome: Operation finished means the command ended, not that login succeeded. There is no force-reauthorization or switch-account control.

If Pi provides an authorization link, open it and complete authentication in your browser. If the callback cannot reach the runtime—for example, with a remote or container deployment—paste the full redirected URL into the dialog when prompted.

Logout removes the server’s local Pi credentials and disconnects its authenticated connection. Other sessions using the same saved credentials are also affected. It does not disable the server configuration or revoke access at the provider. To revoke access, use the provider’s account settings.

Cancel requests that pending UI or future prompts stop. It may not immediately stop browser approval, token exchange, or reconnection already in progress; credentials may already have been saved if you cancel after approval.

Pi owns OAuth tokens and server reconnection, storing MCP credentials in the active profile’s mcp-auth.json, separate from model-provider authentication. Ordinary /mcp commands entered in Chat still use Pi’s inline extension UI.

After updating PI WEB, manually restart the session daemon to activate this flow. A browser reload or web/API restart is insufficient. For the systemd user service, run systemctl --user restart pi-web-sessiond from outside its hosted sessions; restarting interrupts active sessions and terminals.

Provider safety and logging
  • Provider registrations/configuration are a startup snapshot. /reload cannot rebuild it.
  • Accepted model-list updates are machine-wide; if two workspaces register lists for one provider, the last registration wins.
  • Model entries can override provider URLs/headers. Pi extensions remain trusted code; this is not a security boundary.
  • Provider decisions are recorded in daemon logs, not browser notifications. Entries omit provider configuration and credentials. See provider extension troubleshooting for ignored changes.

Environment overrides

Every nondeprecated runtime core key has a PI_WEB_<SNAKE_CASE_KEY> override. These enforce values over machine, supported project, and applicable browser choices. Look up the setting above for scope and restart requirements. Offline plugin recovery state is managed separately by the recovery CLI.

Strings/numbers use scalar values; object/array settings use JSON. Container JSON variables retain their existing names and enforce only supplied namespace leaves, including pathAccess.allowedPaths and plugin leaves; {} enforces none. Atomic settings lock the whole value. Boolean inputs accept only true/false (case-insensitive) or 1/0. Invalid supplied policy fails startup rather than being ignored. Unknown fields in declared core containers, including misspellings in pathAccess, uploads, and attachments, are errors. Plugin environment envelopes accept only enabled and settings; keys inside settings remain plugin-owned.

PI_WEB_INSTALLATION_NAME='Build lab'
PI_WEB_BASE_PATHS='["/opt/reference"]'
PI_WEB_UPLOADS='{"defaultFolder":"manual/uploads"}'
PI_WEB_DEFAULT_LOCALIZATION='{"timeZone":"UTC"}'
PI_WEB_PLUGINS='{"git":{"settings":{"workspaceDiscoveryHooks":false}}}'

Unset a variable to remove enforcement; empty is not a general reset syntax. Legacy empty host, port, allowed-hosts, upload-limit, and archive-directory overrides remain ignored. Runtime markers such as PI_WEB_SESSION are not config policy.
