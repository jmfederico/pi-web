# Contributing

Bug reports, questions, feature requests, and pull requests are welcome.

## Issue and pull request descriptions

Use plain, concise language. State what happened or what should change, and why it matters.

Start with `## What and why`, using **250 words maximum**. The opening must stand alone without requiring code or appendix reading. For bugs, include expected/actual behavior and only the reproduction steps needed to understand the report.

Put implementation walkthroughs, file inventories, lengthy logs, and detailed verification in one optional collapsed appendix. Keep essential decisions, risks, and questions in the opening.

```markdown
## What and why

Reconnecting from a phone loses the selected session.
The same session should remain selected so work can continue
without searching for it again.

<details>
<summary>Technical details — optional reading</summary>

Optional logs, investigation, and verification.

</details>
```

### One decision per issue

Keep independently decidable requests in separate linked issues. Related symptoms and necessary steps toward one outcome can stay together. A shared context alone does not make separate proposals one request.

### AI-assisted submissions

You may use AI to prepare a submission. Keep agent working notes out of the opening, and do not imply human experiences or approval that did not occur. AI-written messages must end with:

> *Automatically generated by the user's AI workflow.*

### Description reviews

Description labels record whether the description is clear, needs clarification, or needs rewriting. They do not confirm a bug or accept or reject a proposal. Type labels distinguish bugs, support requests, and features.

Review comments identify unmet requirements; you decide how to address them. If you disagree with an assessment, you can ask a maintainer to review it.
